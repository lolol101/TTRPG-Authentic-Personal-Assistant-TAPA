# BACKLOG — TAPA

Источник правды по задачам. Берём один пункт за раз (см. `CLAUDE.md`, раздел 2).

## Контекст и уже принятые решения

Зафиксировано в переписке до начала кода:

- **Целевая платформа**: веб-приложение как основной интерфейс. LLM/RAG —
  отдельный сервис со своим HTTP API, во время пилота крутится локально (Ollama),
  провайдер LLM переключается конфигом (Ollama ↔ облако), без переписывания веб-части.
- **Система правил для MVP**: Pathfinder 2e, только открытый контент (ORC/SRD) —
  см. `.claude/rules/ml-system-design.md`.
- **Аутентификация**: нужна с самого начала — многопользовательский режим,
  у каждого свои персонажи.
- **Лист персонажа**: полноценный, референс — лист на Roll20. Интерактивные броски
  кубов и подобное — см. «Отложено» ниже.
- **Стек**:
  - `web-backend`: Python + FastAPI (пользователь уверен в Python).
  - `web-frontend`: React + TypeScript + Vite. Типы для листа персонажа —
    генерируются из OpenAPI-схемы бэкенда, не пишутся вручную дважды.
  - `llm-service`: Python, обёртка над существующим LangGraph-графом
    (Primary/RAG агенты, Chroma) из черновика.
  - Предполагаемая раскладка монорепо (ещё не согласована окончательно):
    ```
    /apps
      /web-frontend
      /web-backend
      /llm-service
    /packages
      /pf2e-data
    /infra
    ```
- **Git-процесс**: ассистент работает автономно в feature-ветках (создаёт,
  коммитит, пушит в `origin` — у пользователя есть доступ к `lolol101/...`),
  `main` защищена — мёрж только через PR и ревью человека.
- **Инфраструктура пилота**: SQLite вместо Postgres на старте (без Docker);
  переезд на Postgres/Docker Compose — отдельная задача, когда встанет вопрос
  хостинга. На машине для разработки доступна RTX 5080 (16GB VRAM) для Ollama —
  не обязательно ограничиваться мелкими моделями вроде `qwen2.5:7b-instruct`
  из черновика.
- **Аутентификация в первой ветке**: делаем по-настоящему сразу, не заглушкой —
  таблица `users`, регистрация/логин, JWT bearer-токен, `/auth/me`.

## Черновик в репозитории — что с ним делать

В корне сейчас лежит черновая реализация (`agents_core/`, `bot/`, `config/`,
`graph/`, `services/`, `tasks/`, `tests/`): aiogram-бот, LangGraph-роутинг
Primary → RAG, Chroma + e5-large-v2, скрапер Archives of Nethys. Решено: убрать
в `legacy/` как референс (не эталон) отдельным коммитом/веткой перед стартом
новой структуры — код и промпты RAG-роутинга остаются под рукой для
переиспользования в `apps/llm-service`.

## Направление продукта

Зафиксировано после разбора рынка (сентябрь 2026). Это контекст для
приоритетов, а не список задач.

### Кому и в каком порядке: сначала игрок, потом ГМ

Решение принято сознательно — вопреки тому, что платят в НРИ за инструменты ГМа
($9–13/мес у Archivist, Saga20, GM Assistant, Tabletop Arc), а инструменты
игрока стоят $5–7 разово (Pathbuilder) или бесплатны (Archives of Nethys,
Pathbuilder, Wanderer's Guide).

Причина: работа ГМа строится вокруг тех же сущностей — персонажей, правил,
лора. Бюджет встречи считается от уровня и состава партии, сокровища ложатся в
слоты персонажей, план левел-апа — это диффы к листам. Значит лист персонажа,
корпус правил и движок проверяемых правок — общий фундамент для обеих сторон,
и порядок «игрок → ГМ» не выбрасывает работу.

**Следствие, которое надо держать в голове при каждой правке листа:** лист —
это основа, а не конечный продукт. В общем коде не должно закрепляться
допущение «у персонажа ровно один владелец, и он же игрок» — иначе понятие
«партия» придётся доклеивать поверх готового. См. §3 `CLAUDE.md` о переносимых
фичах.

### Чем отличаемся

Пересечение «ассистент + гарантированно верные правила» на рынке пусто:

- AI-инструменты ГМа (Archivist, Saga20, StormScape, Tabletop Arc) работают с
  нарративом — заметки, рекапы, мир; верность правил они не обещают;
- AI-модули Foundry (FoundryAI с 40+ инструментами, RPGX, Smart Chat) строят
  RAG по миру пользователя (журналы, актёры), а не по книгам правил, и пишут в
  лист напрямую, без шлюза;
- правило-точные инструменты (Pathbuilder, Pathfinder 2e Nexus, D&D Beyond)
  ассистента не имеют — D&D Beyond свой «Rules Assistant» закрыл, свернув
  работу в семантический поиск по сайту.

Отличие TAPA формулируется не как «AI для PF2e», а как **ассистент, который не
может соврать про число**: математика считается кодом, правка проходит через
белый список путей и подтверждение игрока, цитата ведёт на пинованный коммит,
в индекс попадает только ORC/OGL. Это ровно то, что сообщество называет главной
проблемой AI за столом (выдуманные правила и статблоки), и ровно то решение,
к которому там приходят: отделять нарратив от детерминированного движка правил.

### Что меряем, пока не меряем выручку

Цель ближайшего этапа — востребованность и удобство, а не деньги. Значит нужны
числа, а не мнения:

1. **Доля принятых правок** — сколько предложений ассистента игрок применил.
   Численное определение фразы «ассистент меня понимает», и метрика, которой
   у конкурентов нет: у них нет самой механики подтверждения. Задача — ниже.
2. Доля вопросов, после которых игрок всё равно пошёл в Archives of Nethys.
3. Время сборки персонажа с нуля (у Pathbuilder — минуты; мерить секундомером
   на живом человеке).
4. Возврат через неделю: сессии играются раз в неделю, дневные метрики врут.
5. Не метрика, а порог: процент прохождения golden-набора. Ниже какого-то
   уровня остальное не имеет значения — неверное правило за столом дороже
   отсутствия ответа.

### Язык: решение отложено, но у него есть цена

Интерфейс русский, корпус английский (Foundry-паки). Английский рынок больше
на порядок-полтора: PF2e — устойчивый номер два после D&D 5e, а среди тех, кто
уже платит за цифровые инструменты, её доля выше своей доли на рынке вообще
(Foundry VTT, отчёт за 2025: 5e 64.28%, PF2e 30.52%).

i18n сейчас не ставим — это спекулятивная работа (§2). Но знаем цену отсрочки:
стоимость разворота растёт линейно с числом русских строк в JSX. Сегодня это
неделя, после планировщика ГМа — месяц.

## Текущий пункт (в работе)

**Лист: карточки, компоновка, разделение систем + отдельная вкладка чата.**
Замечания с разбора листа:

1. **Каждый заголовок в листе раскрывается и сворачивается.** Сейчас всё
   вывалено в одну кучу и читать невозможно.
2. **Другая компоновка.** Блоки идут строго друг за другом — получается хаос;
   нужна группировка, а не одна длинная лента.
3. **Предметы, черты и заклинания можно добавлять, менять и удалять.** Черты
   раньше были прибиты к печатным слотам бланка без возможности добавить свою.
4. **Полноценные карточки.** У каждого предмета, черты и заклинания в книге
   свой набор полей (дескрипторы, требования, вес, цена, уровень, действия) —
   лист должен их хранить, а не одну строку с названием.
5. **Разделение по системам правил** видно при создании персонажа, а не только
   в коде.
6. **Чат — отдельная вкладка** с историей сообщений, убран из «Правил».

Сделано ранее: `Character` + CRUD с проверкой владельца, лист PF2e по
официальному бланку в 4 вкладках, ассистент читает лист, golden-набор evals.

## Pathfinder 2e

**Лист персонажа у каждой системы правил свой**, поэтому всё специфичное для
PF2e вынесено в отдельные модули и не смешивается с общим кодом:

- фронт — `apps/web-frontend/src/rulesets/pf2e/` (домен, типы листа, вкладки,
  компоненты бланка);
- бэкенд — `apps/web-backend/app/rulesets/pf2e/` (`rules.py` — математика,
  `context.py` — рендер листа для ассистента);
- у `Character` есть поле `ruleset` (по умолчанию `pf2e`), а `sheet_data` для
  общего кода — просто JSON: ни один общий модуль не знает полей PF2e.

Добавление второй системы = новый каталог `rulesets/<система>/` с её листом,
без правок общего кода.

### Терминология

Следуем официальному русскому «Бланку персонажа» (Paizo, 2021), а не кальке с
английского: **ВЫН** (не ТЕЛ), **ЛВК** (не ЛОВ), **Испытания** (не спасброски),
**Внимание/Восприятие**, **Мистицизм** (не Магия), **Исполнение** (не
Выступление), **ПЗ** (не ХП), **Умение** = ранг владения (И/Э/М/Л —
Изученный / Экспертный / Мастерский / Легендарный). Игроки читают печатный
бланк, приложение должно говорить теми же словами.

### Что в листе есть

Четыре вкладки по четырём страницам бланка:

1. **Основное** — шапка, характеристики (модификатор и значение независимо),
   класс брони с владением категориями брони, щит, ПЗ с составом и при
   смерти/ранением, испытания, внимание, классовая СЛ, владение оружием,
   удары ближнего и дальнего боя с уроном, навыки, знания, состояния, языки.
2. **Черты и снаряжение** — черты народа/навыков/общие/классовые по
   уровневым слотам бланка, снаряжение тремя колонками с весом и настройкой,
   нагруженность (5 + СИЛ) и максимум (10 + СИЛ), монеты.
3. **Личность** — портрет, внешность, личность, заметки кампании, действия и
   занятия, свободные и ответные действия.
4. **Заклинания** — атака заклинанием и СЛ, традиция, подготавливающий или
   спонтанный, ячейки по кругам, фокальные пункты, списки заклинаний.

### Карточки предметов, черт и заклинаний

Каждая сущность — не строка с названием, а карточка с полями, как в книге.
Состав полей выверен по официальным правилам (Archives of Nethys, «Reading
Items» / «Reading Spells») и по разметке карточек на pf2.ru:

- **Предмет** — уровень, цена, вес, применение (носится/держится/встроен),
  руки, редкость, дескрипторы, активация (действия, частота, триггер,
  требования), источник, описание.
- **Черта** — уровень, тип (народа / классовая / навыка / общая / архетипа),
  редкость, дескрипторы, предварительные условия, частота, триггер,
  требования, действия, источник, описание, «Особое».
- **Заклинание** — круг, редкость, дескрипторы, традиции, Сотворение
  (действия и компоненты), Дистанция, Область, Цели, Защита, Длительность,
  источник, описание, Повышение.

Содержимое заполняется **вручную**; автозаполнение из каталога — отдельный
пункт ниже. Поэтому у каждой карточки есть поле «источник», которое потом
свяжется с каталогом.

### Чего в листе ещё нет

- Настройка предметов ограничивается числом (макс. 10), но не проверяется.
- Значение характеристики и модификатор не связаны: рядом показывается
  подсказка «по значению +N», но поле не перезаписывается. В ремастере PF2e
  значений уже нет, и жёсткая связка сломала бы игру по нему.
- Броски кубов — сознательно отложены, см. «Отложено».

## Следующие пункты

### Лог исхода предложенных правок

Первая метрика удобства из раздела «Направление продукта». Сейчас у
`ChatMessage` есть только флаг `applied` на весь ход, и ставится он, когда
применять больше нечего; частичное применение по разделам живёт лишь на
странице. Отказа не видно вовсе: игрок, который просто проигнорировал
предложение, не оставляет следа, а «не применено» смешивает «отказался» и
«ещё не дошли руки».

Нужен отдельный, не привязанный к чату и к PF2e, ряд на каждое предложение:
что предложили (путь, раздел, была ли правка проверена расчётом) и чем
кончилось. Отдельная таблица, а не колонка: `init_db()` вызывает
`create_all`, который добавляет недостающие таблицы, но **не** добавляет
недостающие колонки — новая колонка в `ChatMessage` молча не появится в живой
`dev.db`. Новую таблицу не забыть внести в список моделей в `core/migrate.py`.

Открытый вопрос (решать до кода): как фиксировать отказ — явной кнопкой
«Отклонить» рядом с «Применить» (чистый сигнал, но правка UI) или неявно, по
тому, что предложение осталось непринятым к следующему вопросу (без правок UI,
но сигнал шумный).

### Планировщик ГМа — будущий пункт, не сейчас

Продолжение раздела «Направление продукта»: делаем **не** VTT (карты, токены,
туман войны, броски — это Roll20 и Foundry, соло-разработчику там делать
нечего), а планирование.

Почему это ложится на текущую архитектуру лучше, чем вопросы по правилам:
в PF2e подготовка — это **детерминированные таблицы** (XP-бюджет встречи по
уровню угрозы, стоимость существа относительно уровня партии, сокровища по
уровню). Значит считает код, а LLM только объясняет и подбирает — та же схема,
что уже работает в листе, и модель не может ошибиться в числах, потому что
числа не её. Данные для этого уже лежат в Foundry-паках.

Разбивка, когда дойдут руки: бюджет встречи → подбор существ из паков по
бюджету → сокровища по уровню партии → объяснение от LLM со ссылками.
Предварительное условие — понятие «партия» (см. «Кому и в каком порядке»).

### Чаты: несколько независимых диалогов на сервере — сделано

`Chat` и `ChatMessage` лежат в базе, список/создание/переименование/удаление
работают, история уходит в модель вместе с вопросом. Принятые решения:

- **чат помнит выбор**: персонаж и система правил — поля чата, а не каждого
  вопроса. Диалог, меняющий персонажа на полпути, подсовывал бы модели лист,
  противоречащий тому, что она сказала два хода назад;
- **лимит контекста — скользящее окно по бюджету токенов** (3000 по умолчанию,
  `history_token_budget`). Выбрасываются целые реплики с самого старого конца,
  и ответ не остаётся без своего вопроса. Сколько поместилось — возвращается
  наружу и рисуется чертой в ленте: бюджет, который молча забывает, хуже, чем
  отсутствие памяти;
- **уточняющий вопрос ищется вместе с предыдущим** («а если он в тяжёлой
  броне?» сам по себе не находит ни одной страницы правил);
- **квоты**: 50 чатов, 500 сообщений в чате, 4000 символов на сообщение.

Осталось по этой теме:

- **авто-саммари выпавшей части** — сознательно отложено: это +1 вызов модели
  на сообщение и резюме, которое уже не проверить по источникам. Вернуться,
  если окажется, что окна реально не хватает;
- **точный счёт токенов** вместо эвристики «2.5 символа на токен». Нужен
  токенизатор (новая зависимость) — по §6 CLAUDE.md согласовывать отдельно;
- **старая история из `localStorage` не перенесена** и перенесена не будет:
  оформить чужие сохранённые реплики как ответы, которые ассистент на самом
  деле давал, нечестно;
- **привязка чата к кампании/сессии** («чат по сессии») — когда появятся сами
  кампании.

### Каталог контента PF2e и автозаполнение карточек

Карточки предметов, черт и заклинаний сейчас заполняются вручную. На pf2.ru
лежит готовый каталог: **5537 черт, 2566 предметов, 1888 заклинаний**, 365
единиц оружия, 325 предысторий, 274 наследия, 196 архетипов — и на каждой
странице указан источник («Основная книга игрока»). Задача:

- расширить ingestion (`packages/pf2e-data`) на эти разделы, сохраняя поля
  карточки, а не только текст для поиска;
- поиск по каталогу в листе: начал печатать название — выбрал — карточка
  заполнилась сама, с проставленным источником;
- ручное редактирование остаётся: домашние правила и вещи из книг, которых в
  каталоге нет.

Подводные камни, которые уже видно:

- у PF2e две редакции — **Legacy** (2019) и **Remaster / Player Core** (2023),
  и pf2.ru даёт обе версии страницы. Нужно решить, какую тянуть и как помечать;
- **URL на pf2.ru содержат пробелы** (`/feats/rock runner`). Это не баг нашего
  парсера — так лежит в их `sitemap.xml`; при запросах URL надо кодировать, а
  в источниках показывать читаемо.

### Вторая система правил

Каркас готов: реестр систем (`src/rulesets/registry.ts`), поле `ruleset` у
персонажа и выбор системы при создании. Чтобы добавить систему, нужен новый
каталог `rulesets/<система>/` со своим листом и (если ассистент должен её
понимать) свой `rules.py` + `context.py` на бэкенде. Общий код не трогается.

### Корпус правил: источник — паки Foundry (сделано)

Источник правил — не краулер по pf2.ru, а структурированный JSON из
[foundryvtt/pf2e](https://github.com/foundryvtt/pf2e) под OGL/ORC.
Конвертер: `packages/pf2e-data/app/foundry.py`, запуск —
`uv run python -m app.foundry_cli --packs <checkout>/packs/pf2e`.

**13 494 чанка** против 2 441 у краулера, без sitemap, троттлинга и банов.

Почему сменили: pf2.ru отвечает `403 Forbidden: IP is banned` на запросы с
нашей сети, но главное — собранный корпус и так был дырявым. По логам
`monsters` потерял 2662 страницы, `spells` и `equipment` — сопоставимо: всё
это блокировки, которые старый краулер принимал за мёртвые ссылки.

Что закрылось само собой вместе со сменой источника:

- **Legacy / Remaster** — в каждой записи стоит флаг `publication.remaster`,
  так что выбор проверяется, а не угадывается. Берём только Remaster;
  5 877 доремастерных записей отброшены.
- **Лицензия** — `publication.license` проштампована в каждой записи, индексируем
  только `ORC`/`OGL`. Раньше лицензионная чистота была допущением.
- **Парсеры под шаблоны страниц** (ancestries, classes, rituals, hazards, armor)
  — не нужны: у JSON один формат на все разделы.
- **Пробелы в URL pf2.ru**, протухшие ссылки в sitemap, инкрементальный
  докачивающий прогон — всё это про краулер, которого больше нет в тракте.

Русский корпус pf2.ru не удалён: лежит в `{TAPA_DATA_DIR}/pf2e-data/chunks-pf2ru-archive`,
краулер и его тесты в репозитории остались рабочими.

**Что осталось открытым:**

1. **Язык.** Foundry-паки английские — это регресс против русского pf2.ru.
   Вопросы у пользователя русские, ответы модели русские, а цитаты правил
   теперь английские. Готового полного русского датасета под открытой
   лицензией найти не удалось. Варианты: жить так, искать перевод, или
   переводить корпус машинно (тогда — с пометкой в метаданных, что это
   перевод, а не источник).
2. **Бестиарий прозой не покрыт.** Монстры, NPC и опасности лежат в паках
   структурными статблоками без текста описания — фильтр по лицензии их не
   теряет (текста там и нет), но раздел `monsters`, который был у pf2.ru,
   эта замена не заменяет. Нужен отдельный конвертер статблока в текст.
3. **Качество поиска на масштабе.** `k=5` по 13,5 тыс. чанков — не то же, что
   по 2,4 тыс.: нужен фильтр по разделу в метаданных (вопрос про заклинание
   не должен тянуть черты) и расширенный golden-набор, иначе деградацию
   никто не заметит. Метаданные для этого уже есть: `category`, `traits`,
   `source_book`, `language`.
4. **Обновление корпуса.** Паки живут в git: обновление — это `git pull` и
   повторный прогон конвертера. Ссылки-цитаты пинятся на коммит, так что
   после обновления они продолжают указывать на тот текст, по которому
   отвечали. Автоматизации пока нет.

### Доступ извне: поделиться с друзьями

Разобранные варианты (LLM крутится на домашней 5080, это определяет выбор):

- **Cloudflare Tunnel** — бесплатно, публичный HTTPS-адрес, без проброса
  портов, белого IP и раскрытия домашнего IP. Ставится за вечер. Работает,
  только пока ПК включён.
- **Веб в облаке + LLM домой через туннель** — приложение доступно всегда, а
  когда ПК выключен, модель уходит на облачный резерв (уже сделано). Дороже
  и сложнее: нужен переезд на Postgres.
- **Tailscale** — приватная сеть, друзьям надо ставить клиент. Безопасно, но
  это не «скинул ссылку».

**Публиковать в текущем виде нельзя.** Что нужно сделать до этого:

1. ~~**JWT-ключ.**~~ **Сделано.** Дефолта больше нет: `verify_security_config()`
   в lifespan роняет старт, если ключ пуст, короче 32 символов или совпадает с
   заглушкой из репозитория. Ключ берётся только из `.env`, `.env.example`
   содержит команду генерации. Побочный эффект: токены, выписанные старым
   дефолтным ключом, больше не действуют — придётся войти заново.
2. **Не публиковать dev-сервер Vite.** Он не рассчитан на внешний трафик;
   нужна сборка и раздача статики.
3. **Ограничение частоты запросов.** Публичный `/llm/ask` без лимитов — это
   чужие токены за наш счёт и нагрузка на GPU.
4. **Закрытая регистрация.** Иначе аккаунт заведёт любой, у кого есть ссылка:
   код приглашения или белый список почт.
5. **CORS.** Сейчас мидлвари нет вообще — при раздельных доменах фронта и
   бэкенда её придётся настроить явно и узко.

### Ассистент правит лист персонажа — что осталось

Основное сделано: инструмент `propose_sheet_change`, белый список путей на
бэкенде, дифф «было → стало» в чате и кнопка подтверждения. Осталось:

- **история изменений** в листе: кто и когда поменял, откат;
- **правка карточек** — сейчас доступны только числа и ранги; добавить в лист
  предмет или заклинание целиком ассистент пока не может;
- **проверка правил при правке**: сейчас диапазоны проверяются формально
  (0…4 для состояний), но не сверяются с правилами PF2e — например, что ранг
  владения не может расти выше допустимого на этом уровне.

### Свести математику правил PF2e в одно место

Сейчас расчёт (ранг владения с учётом уровня, итог характеристики, максимум ПЗ)
продублирован: `web-frontend/src/rulesets/pf2e/domain.ts` и
`web-backend/app/rulesets/pf2e/rules.py`.
Дублирование сознательное — фронту расчёт нужен для живого листа, бэкенду для
ассистента, и просить модель считать арифметику нельзя. Обе стороны покрыты
зеркальными тестами, так что расхождение уронит сборку. Но при росте правил
лучше свести к одному источнику: считать на бэкенде и отдавать готовые значения
через API.

## Принятые решения по UI

- **Компонентная база — `shadcn/ui` + Tailwind v4**. Выбрано вместо готового
  шаблона-дашборда целиком: компоненты копируются в репозиторий
  (`src/components/ui`), а не тянутся как внешняя зависимость, и мы не наследуем
  чужой роутинг, моки и десяток ненужных страниц. Иконки — `lucide-react`.
- **Визуальный стиль — «Surviving the Dungeon»** ([референс на Behance](https://www.behance.net/gallery/195363551/Surviving-the-Dungeon)):
  бумажная фактура вместо плоского белого, чернильно-синий графит как основной
  цвет, приглушённый бордовый — редкий акцент только на главных действиях,
  рукописный шрифт для заголовков и серифный для текста. Настроение —
  дружелюбный блокнот игрока, а не мрачное подземелье.
- **Принцип листа персонажа взят с листа Roll20 PF2e**: характеристика — это не
  одно число, а именованная сумма компонентов (характеристика + ранг владения с
  учётом уровня + бонус предмета + временный модификатор + штраф брони). Каждый
  компонент правится отдельно, итог считается сам. В БД типизированными
  колонками лежит только то, что нужно запрашивать бэкенду; разбивка по
  компонентам — в JSON `sheet_data`.
- Алиас `@/*` → `src/*`.
