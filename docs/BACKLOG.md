# BACKLOG — TAPA

Источник правды по задачам. Берём один пункт за раз (см. `CLAUDE.md`, раздел 2).

## Контекст и уже принятые решения

Зафиксировано в переписке до начала кода:

- **Целевая платформа**: веб-приложение как основной интерфейс. LLM/RAG —
  отдельный сервис со своим HTTP API, во время пилота крутится локально (Ollama),
  провайдер LLM переключается конфигом (Ollama ↔ облако), без переписывания веб-части.
- **Система правил для MVP**: Pathfinder 2e, только открытый контент (ORC/SRD) —
  см. `.claude/rules/ml-system-design.md`.
- **Аутентификация**: нужна с самого начала — многопользовательский режим,
  у каждого свои персонажи.
- **Лист персонажа**: полноценный, референс — лист на Roll20. Интерактивные броски
  кубов и подобное — см. «Отложено» ниже.
- **Стек**:
  - `web-backend`: Python + FastAPI (пользователь уверен в Python).
  - `web-frontend`: React + TypeScript + Vite. Типы для листа персонажа —
    генерируются из OpenAPI-схемы бэкенда, не пишутся вручную дважды.
  - `llm-service`: Python, обёртка над существующим LangGraph-графом
    (Primary/RAG агенты, Chroma) из черновика.
  - Предполагаемая раскладка монорепо (ещё не согласована окончательно):
    ```
    /apps
      /web-frontend
      /web-backend
      /llm-service
    /packages
      /pf2e-data
    /infra
    ```
- **Git-процесс**: ассистент работает автономно в feature-ветках (создаёт,
  коммитит, пушит в `origin` — у пользователя есть доступ к `lolol101/...`),
  `main` защищена — мёрж только через PR и ревью человека.
- **Инфраструктура пилота**: SQLite вместо Postgres на старте (без Docker);
  переезд на Postgres/Docker Compose — отдельная задача, когда встанет вопрос
  хостинга. На машине для разработки доступна RTX 5080 (16GB VRAM) для Ollama —
  не обязательно ограничиваться мелкими моделями вроде `qwen2.5:7b-instruct`
  из черновика.
- **Аутентификация в первой ветке**: делаем по-настоящему сразу, не заглушкой —
  таблица `users`, регистрация/логин, JWT bearer-токен, `/auth/me`.

## Черновик в репозитории — что с ним делать

В корне сейчас лежит черновая реализация (`agents_core/`, `bot/`, `config/`,
`graph/`, `services/`, `tasks/`, `tests/`): aiogram-бот, LangGraph-роутинг
Primary → RAG, Chroma + e5-large-v2, скрапер Archives of Nethys. Решено: убрать
в `legacy/` как референс (не эталон) отдельным коммитом/веткой перед стартом
новой структуры — код и промпты RAG-роутинга остаются под рукой для
переиспользования в `apps/llm-service`.

## Текущий пункт (в работе)

**Ассистент читает лист персонажа.** На вкладке «Правила» выбирается персонаж,
лист уезжает в контекст запроса с **уже посчитанными** модификаторами — считает
бэкенд, а не модель: арифметика ровно то, в чём LLM ошибается, и неверный бонус
навыка выглядит так же уверенно, как верный.

Границы: `/llm/ask` теперь требует авторизации (раньше был открытым — платные
вызовы модели без токена), персонаж проверяется на владельца (404, а не 403),
имя игрока и личные заметки в модель не отправляются — по правилу про PII из
`.claude/rules/ml-system-design.md`.

Golden-набор evals — `apps/llm-service/evals/`, запуск вручную против живого
сервиса: `uv run python evals/run_evals.py`. Правило из `ml-system-design.md`
требует прогонять его перед изменением промпта.

Сделано ранее: модель `Character` + CRUD с проверкой владельца, UI листа по
образцу Roll20 (компонентная модель характеристик), состояния и очки героя.

## Следующие пункты

### Чаты: несколько независимых диалогов

Сейчас вопрос по правилам — одноразовый запрос без истории. Нужна возможность
вести **несколько отдельных чатов** и переключаться между ними:

- модель `Chat` (владелец, название, дата) и `Message` (роль, текст, источники);
- история диалога передаётся в LLM как контекст, а не только последний вопрос;
- список чатов в UI, создание/переименование/удаление, переключение;
- отдельный вопрос к обсуждению: привязывать ли чат к персонажу или к кампании
  (например, «чат по правилам» vs «чат по сессии»).

### Ассистент правит лист персонажа (запись)

Чтение листа сделано (см. «Текущий пункт»). Осталась запись:

- ассистент предлагает изменения листа (потратить ХП, отметить состояние,
  поднять ранг владения при левел-апе), пользователь подтверждает — не
  молчаливая правка;
- механика: tool calling поверх существующего CRUD `/characters`, чтобы правки
  шли через ту же валидацию и проверку владельца, а не в обход. Текущая модель
  (`nvidia/nemotron-3.5-lightning:free`) вызов инструментов поддерживает —
  проверено по `supported_parameters` в OpenRouter;
- открытые вопросы: как показывать предложенную правку в UI (дифф перед
  подтверждением); писать ли в лист историю изменений.

### Свести математику правил PF2e в одно место

Сейчас расчёт (ранг владения с учётом уровня, итог характеристики, максимум ХП)
продублирован: `web-frontend/src/lib/pf2e.ts` и `web-backend/app/core/pf2e.py`.
Дублирование сознательное — фронту расчёт нужен для живого листа, бэкенду для
ассистента, и просить модель считать арифметику нельзя. Обе стороны покрыты
зеркальными тестами, так что расхождение уронит сборку. Но при росте правил
лучше свести к одному источнику: считать на бэкенде и отдавать готовые значения
через API.

### Расширение ingestion за пределы `/actions/`

Сейчас в индексе только раздел действий с pf2.ru. Дальше — народы, классы,
заклинания, снаряжение. Отдельно: в URL источников попадают пробелы
(`.../actions/maneuver in flight`) — баг сборки ссылки в парсере, чинить вместе
с расширением.

## Принятые решения по UI

- **Компонентная база — `shadcn/ui` + Tailwind v4**. Выбрано вместо готового
  шаблона-дашборда целиком: компоненты копируются в репозиторий
  (`src/components/ui`), а не тянутся как внешняя зависимость, и мы не наследуем
  чужой роутинг, моки и десяток ненужных страниц. Иконки — `lucide-react`.
- **Визуальный стиль — «Surviving the Dungeon»** ([референс на Behance](https://www.behance.net/gallery/195363551/Surviving-the-Dungeon)):
  бумажная фактура вместо плоского белого, чернильно-синий графит как основной
  цвет, приглушённый бордовый — редкий акцент только на главных действиях,
  рукописный шрифт для заголовков и серифный для текста. Настроение —
  дружелюбный блокнот игрока, а не мрачное подземелье.
- **Принцип листа персонажа взят с листа Roll20 PF2e**: характеристика — это не
  одно число, а именованная сумма компонентов (характеристика + ранг владения с
  учётом уровня + бонус предмета + временный модификатор + штраф брони). Каждый
  компонент правится отдельно, итог считается сам. В БД типизированными
  колонками лежит только то, что нужно запрашивать бэкенду; разбивка по
  компонентам — в JSON `sheet_data`.
- Алиас `@/*` → `src/*`.
