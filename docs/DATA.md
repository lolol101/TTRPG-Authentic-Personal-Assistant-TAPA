# Данные: где лежат и как перенести на другой ПК

Всё, что приложение **не может пересоздать само**, лежит в одной папке.
Переезд на другую машину — это копирование этой папки плюс трёх файлов `.env`.

## Где

Путь задаётся переменной `TAPA_DATA_DIR` в `.env` каждого сервиса. Если её не
задать, каждый сервис хранит данные рядом с собой в `./data` — так работает
свежий клон без настройки.

Сейчас на этой машине: `D:/TAPA-data` (на `C:` было всего 8 ГБ свободно).

```text
D:/TAPA-data/
  web-backend/
    dev.db              # пользователи и персонажи (SQLite)
  llm-service/
    vector_db/          # индекс Chroma — векторы правил
  pf2e-data/
    chunks/             # разобранные куски книг (.jsonl)
    html_cache/         # скачанные страницы pf2.ru
```

Что из этого действительно незаменимо:

| Папка | Потеря означает |
|---|---|
| `web-backend/dev.db` | **безвозвратно**: персонажи и аккаунты |
| `pf2e-data/chunks` | пересобирается из `html_cache` за минуты |
| `llm-service/vector_db` | пересобирается из `chunks` за минуты |
| `pf2e-data/html_cache` | пересобирается только повторным скачиванием — **часы** |

## Перенос на другой ПК

1. Скопировать папку `D:/TAPA-data` целиком (внешний диск, сеть — как удобно).
2. Скопировать три файла `.env` — они **не** в git, потому что содержат ключи:
   `apps/web-backend/.env`, `apps/llm-service/.env`, `packages/pf2e-data/.env`.
3. На новой машине склонировать репозиторий и поставить зависимости
   (`uv sync` в каждом проекте, `npm install` во фронтенде).
4. Если путь к данным другой — поправить `TAPA_DATA_DIR` в этих трёх `.env`.
5. Запустить: `uv run python scripts/check_data.py` из корня репозитория —
   скрипт скажет, всё ли на месте, до того как ты полезешь в приложение.

### Что учесть

- **`JWT_SECRET_KEY` надо перенести вместе с базой.** Другой ключ — и все
  выданные токены становятся недействительными: придётся входить заново.
  Пароли при этом не теряются, они хранятся хэшами в базе.
- **SQLite не любит копирование на ходу.** Останови `web-backend` перед тем
  как копировать `dev.db`, иначе рискуешь снять файл в середине записи.
- **Индекс привязан к модели эмбеддингов.** Коллекция называется по модели,
  поэтому на машине с другой моделью (например, `fastembed` вместо `bge-m3`
  на GPU) индекс придётся пересобрать из `chunks`. Это минуты, не часы.

## Переезд базы в облако

База персонажей может жить в облачном Postgres — тогда она переживает смерть
диска и не зависит от того, включён ли домашний ПК. Код к этому готов:
`DATABASE_URL` — единственное, что отличает SQLite от Postgres, драйвер
(`psycopg`) уже в зависимостях.

1. Завести бесплатную базу (например, [Neon](https://neon.tech) — 0.5 ГБ,
   без карты) и скопировать строку подключения.
2. **Остановить бэкенд.** Копия SQLite, снятая во время записи, может
   оказаться обрезанной на середине.
3. Перенести:

   ```bash
   cd apps/web-backend
   uv run python ../../scripts/migrate_to_postgres.py \
       --to "postgresql+psycopg://user:pass@host/db?sslmode=require"
   ```

4. Прописать тот же URL в `DATABASE_URL` в `apps/web-backend/.env` и
   запустить бэкенд.

Скрипт отказывается писать в непустую базу: повторный запуск задвоил бы
персонажей. Он же сдвигает последовательности Postgres за перенесённые `id` —
без этого первая же новая запись упала бы на конфликте ключа, причём далеко
от места ошибки.

Что в облако **не** уезжает: векторный индекс правил и HTML-кэш. Индекс
пересобирается из чанков, кэш нужен только чтобы не качать pf2.ru заново.

## Резервная копия

Отдельного формата бэкапа нет и не нужно: копия папки `D:/TAPA-data` и есть
полный бэкап. Достаточно останавливать `web-backend` на время копирования.
