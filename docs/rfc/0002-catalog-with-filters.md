# 0002. Каталог PF2e с фильтрами для подборок и автозаполнения

- **Статус:** черновик
- **Дата:** 2026-10-01

## Вопрос

Как отвечать на вопросы-подборки («подбери арканные заклинания контроля для
волшебника 1-го уровня», «что мне купить на моём уровне») и откуда брать поля
карточки при автозаполнении. Нужно решить, где хранить структурные поля
контента (уровень, круг, традиции, редкость, цена) и кто превращает вопрос в
фильтр. Это новое хранилище данных, поэтому RFC (§0 `CLAUDE.md`).

## Контекст

**Что не работает.** Живой чат 2026-10-01, волшебник 1-го уровня, «Подбери
заклинания контроля, замедления». Поиск вернул одну страницу, Slow 3-го круга,
и ответ получился «в найденном есть только Slow, он вам недоступен». При этом в
индексе **108** арканных заклинаний 1-го круга (подсчёт по строке статблока,
2026-10-01). Поиск берёт k ближайших по смыслу кусков и не умеет «все
арканные, круг ≤ 1, про замедление». Вопросов-подборок в живом использовании
много: из трёх вопросов того чата два были такими.

**Что есть в данных.** Паки `foundryvtt/pf2e` — структурный JSON: у каждой
записи есть `level`, `traits.value`, `traits.rarity`, `traits.traditions`,
`price`, `category`, время сотворения, дистанция и т. д. Конвертер
(`packages/pf2e-data/app/foundry.py`, `_header`) уже читает эти поля, но
**сворачивает их в текст** первой строкой куска: `Spell 3 · Traits: … ·
Traditions: arcane, occult · …`.

**Что есть в индексе.** Метаданные куска в Chroma
(`apps/llm-service/app/ingest.py`, `to_metadata`): `url`, `title`,
`category`, `source_book`, `traits` (строкой), `language`, `ruleset`,
`license`. Уровня, круга, традиций, редкости и цены там нет. В текущей схеме
значения метаданных — только скаляры (это требование уже записано в
`to_metadata`), то есть список традиций полем не положить.

**Что уже умеет код.** Уровень страницы читается из строки статблока
(`apps/llm-service/app/rulesets/pf2e/availability.py`, PR #61) и сравнивается
с `character_level`, который web-backend передаёт числом. Вызов
переписывания запроса (`app/core/query_rewrite.py`) уже идёт на каждом
вопросе и возвращает структуру через инструмент. Автозаполнение карточек
стоит в бэклоге отдельно («Каталог контента PF2e и автозаполнение
карточек»); поля карточки перечислены в `SHEET_CHANGE_TOOL`.

**Ограничения.** Специфика PF2e живёт в `rulesets/pf2e/` (§3); общий код не
знает полей системы. Полная переиндексация эмбеддингов на этой машине — часы
(CPU, ~96 кусков/мин); разбор паков без эмбеддингов — минуты.

## Варианты

Развилок две: **где хранить** структурные поля и **кто строит фильтр**.

### Где хранить

#### A. Поля в метаданных Chroma

Добавить в `to_metadata` `level`, `rarity`, `price_cp`, `kind` и булевы флаги
традиций (`trad_arcane` и т. д.), фильтровать `where` (`$lte`, `$eq`) и
ранжировать по близости внутри фильтра.

- Хорошо: одно хранилище, фильтр и поиск по смыслу в одном запросе.
- Плохо: каждое новое поле — полная переиндексация (часы). Списки
  приходится разворачивать во флаги. Поля PF2e оказываются в общей схеме
  метаданных. Для автозаполнения карточки нужен **весь** набор полей
  (предпосылки, частота, триггер), а метаданные для этого не предназначены.
- Если окажется неверным: поля остаются в индексе мёртвым грузом, откат —
  ещё одна переиндексация.

#### B. Отдельный каталог: таблица SQLite, собираемая вместе с кусками

Тот же прогон конвертера пишет рядом с `.jsonl` файл каталога: по записи на
сущность, общие колонки (`ruleset`, `kind`, `name`, `level`, `url`,
`license`) и JSON-колонка с полями, специфичными для системы (традиции,
редкость, цена, поля карточки). Онлайн код фильтрует каталог SQL-запросом,
получает кандидатов и ранжирует их по близости уже существующих кусков с тем
же `url`.

- Хорошо: настоящие структурные запросы (диапазоны, списки, `LIKE` по
  названию). Собирается за минуты, без эмбеддингов. Та же таблица отдаёт
  полную карточку для автозаполнения. `sqlite3` есть в стандартной
  библиотеке — новой зависимости нет. Специфика PF2e остаётся в JSON-колонке
  и в `rulesets/pf2e/`.
- Плохо: второе хранилище, его надо держать в паре с индексом (собирать тем
  же прогоном с того же коммита паков). Понадобится миграционная дисциплина
  схемы каталога.
- Если окажется неверным: файл каталога удаляется, индекс не тронут.

#### C. Без хранилища: модель листает индекс сама

Давать модели несколько поисков подряд (инструментом), пока она не соберёт
список.

- Хорошо: ничего не строить.
- Плохо: k ближайших не перечисляют «все арканные 1-го круга» ни за один,
  ни за пять запросов. Каждый круг — вызов модели и квота GigaChat. Числа
  (круг, цена) снова проходят через модель.
- Если окажется неверным: потрачены вызовы, ответы как сейчас.

### Кто строит фильтр

#### 1. Тот же вызов переписывания запроса

Инструмент `search_the_rulebooks_in_english` получает необязательное поле
`filter` (вид, признаки, традиция, «по уровню персонажа»). Код дополняет
фильтр тем, что знает сам: уровень персонажа, традицию класса из листа
(таблица в `rulesets/pf2e/`).

- Хорошо: ни одного нового вызова; числа ограничений ставит код.
- Плохо: инструмент переписывания усложняется; фильтр, который модель
  неверно поняла, сузит выдачу до неверного — нужен откат на обычный поиск
  при пустом результате.

#### 2. Отдельный инструмент поиска по каталогу, вызываемый моделью ответа

- Хорошо: модель сама решает, нужен ли каталог.
- Плохо: +1 вызов на каждый вопрос-подборку и диалект функций GigaChat
  (`functions` вместо `tools`, см. `gigachat.py`) — больше мест для сбоя.

## Рекомендация

**B + 1.** Каталог в SQLite рядом с кусками, фильтр — из уже существующего
вызова переписывания, ограничения по персонажу — кодом.

Это единственное сочетание, где «круг ≤ доступного» и «традиция = арканная»
проверяет код, а не модель, и которое одновременно закрывает автозаполнение
карточек из бэклога. Честно о плохом: появляется второе хранилище, и
рассинхрон каталога с индексом станет новым классом ошибок — его надо ловить
проверкой при старте (один и тот же коммит паков в обоих).

## Что дальше

- Схема каталога и сборка его тем же прогоном конвертера (`packages/pf2e-data`).
- Чтение каталога в `llm-service`, PF2e-часть — в `app/rulesets/pf2e/`.
- Поле `filter` в инструменте переписывания и откат на обычный поиск при
  пустом результате.
- Golden-случаи на подборки: «арканные заклинания 1-го круга про
  замедление», «оружие, которым владеет волшебник», «предметы до 1-го уровня
  дешевле 15 зм».
- Автозаполнение карточки из каталога — отдельным пунктом после.
