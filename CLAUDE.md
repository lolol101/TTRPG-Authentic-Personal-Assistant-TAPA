# CLAUDE.md — правила работы над проектом TAPA

Этот файл — инструкции для AI-ассистента (и людей), работающего над репозиторием.
Он задаёт _как_ вести разработку. Что делать по существу — см. `docs/BACKLOG.md`.

> Примечание: этот файл — контекст, а не жёсткая блокировка. Настоящие гарантии
> даёт CI (тесты, линтер, pre-commit) — см. задачу в бэклоге. Держим файл коротким.

---

## 0. Главный принцип: спрашивай раньше, чем делаешь

Прежде чем реализовывать что-либо, что меняет **логику или вид проекта**, ассистент
**останавливается и задаёт вопрос**. Сюда входит всё, что затрагивает:

- модель данных / схему БД / формат листа персонажа;
- контракт API (эндпоинты, форматы запросов/ответов);
- UX и внешний вид (структура страниц, поведение форм);
- выбор/добавление зависимости, библиотеки, сервиса;
- архитектуру, границы сервисов, способ хранения данных.

Для **обратимых внутренних деталей** (имя приватной функции, локальный рефакторинг
внутри модуля) — можно действовать без вопроса. Правило простое: _если решение
трудно откатить или его увидит пользователь — сначала спроси_.

Вопросы задаём честно и по одному, с вариантами ответа, где это уместно.

## 1. Git и ветки

- Ветка `main` **защищённая**: прямые коммиты в неё запрещены.
- Каждая задача — отдельная ветка от актуального `main`.
  Именование: `type/краткое-описание`, где `type` —
  `feat | fix | refactor | test | docs | chore`.
  Пример: `feat/pf2e-character-schema`, `fix/auth-token-expiry`.
- Одна ветка = одна логическая задача. Маленькие PR лучше больших.
- Сообщения коммитов — **Conventional Commits**: `type(scope): summary`.
  Пример: `feat(backend): add character CRUD ownership check`.
- Перед каждым коммитом: прогнать тесты и линтер, убедиться, что зелёные.

**Автономия ассистента:** может самостоятельно создавать ветки, коммитить и
**пушить feature-ветки**. Работает по циклу: ветка → мелкие осмысленные коммиты
(Conventional Commits) → push своей ветки.

**Ассистент НИКОГДА без явного разрешения человека:**
не коммитит и не пушит в `main`; не мёржит/ребейзит в `main` (мёрж — через PR и
ревью человека); не делает `push --force` и не переписывает историю уже
запушенных веток; не делает `git reset --hard` по общим веткам; не удаляет чужие
ветки; не меняет git-настройки.

## 2. Не отклоняться от плана и не раздувать объём

- Источник правды по задачам — `docs/BACKLOG.md`. Берём **один пункт за раз**.
- Реализуем ровно то, что нужно текущему пункту. **YAGNI**: никакого кода «на будущее»,
  спекулятивных абстракций, «заодно переписать вот это».
- Если по ходу видно, что нужен объём за рамками задачи — не делаем молча, а
  **выносим в бэклог** и спрашиваем, брать ли сейчас.
- Расширение архитектуры (новый сервис, слой, паттерн) — только после явного
  согласования (см. раздел 0).

---

## 3. Чистый код

- Следуем **существующей структуре и стилю** репозитория; не рефакторим без причины.
- Функции короткие и с одной ответственностью; понятные имена; без мёртвого кода.
- Python: полные type hints, `ruff` для линта/форматирования, docstring там, где неочевидно «зачем».
- TypeScript: `strict`, без `any` без крайней нужды.
- Предпочитаем доработку существующего модуля добавлению нового слоя.
- Комментарии объясняют «почему», а не «что».

---

## 4. Тесты

- Каждая нетривиальная логика покрывается тестами. Стек: `pytest` (Python).
- Когда заглушка (`TODO`/stub) заменяется реальной реализацией — **вместе с ней добавляем тесты**.
- Приоритет покрытия — там, где цена ошибки высока: авторизация, проверка владельца
  ресурса, валидация правил PF2e, retrieval в RAG. **Жёсткого порога покрытия нет** —
  не гонимся за процентом ради процента, но осмысленное покрытие обязательно.
- Для чистой логики (например, валидация левел-апа PF2e) — **TDD по умолчанию**:
  сначала тест на правило, потом реализация.
- Тест проверяет поведение и граничные случаи, а не факт вызова функции.

## 5. ML system design (для `llm-service` и RAG)

Доменные ML-правила вынесены в **`.claude/rules/ml-system-design.md`** — они
подгружаются автоматически при работе с `apps/llm-service/**` и `packages/pf2e-data/**`.
Ключевое: разделять offline (ingestion) и online (retrieval+генерация), всё через
конфиг, промпты версионируем, evals перед изменением сценария, честность ответа
и лицензионная чистота данных. Подробности — в файле правил.

---

## 6. Границы безопасности

- Секреты/токены/пароли — только через `.env` (в git не коммитим; есть `.env.example`).
- Не добавляем новые внешние зависимости без согласования (раздел 0).
- Необратимые действия (удаление данных, миграции, затрагивающие прод) — с подтверждением.

---

## Как пользоваться этим файлом

При старте работы над задачей: назови пункт из `docs/BACKLOG.md`, создай ветку по
разделу 1, и если есть развилка по логике/виду — спроси до кода (раздел 0).
